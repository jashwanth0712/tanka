# Friction log

Dated log of real problems hit while building on Arkiv. Both frontend and Arkiv-layer entries go here. Newest first.

## 2026-10-18 — Arkiv layer (SDK 0.8.1 on Tiramisu)

- **Faucet is login-gated, so a static app can't fund fresh wallets.** `hub.arkiv.network/faucet` needs a signed-in account (the API returns `401` to a plain `curl`). Our "post with a fresh wallet" flow generates an in-memory key per tab, but that key has 0 GLM, so its first write fails. We surface a "get test GLM at the faucet" message with the wallet address instead. A programmatic faucet (or sponsored/zero-gas writes) would make anonymous posting possible without MetaMask. Repro: `createWalletClient({account: privateKeyToAccount(generatePrivateKey())}).createEntity(...)`.
- **Unfunded write error is opaque.** The same call fails with `Transaction failed: Execution error without revert data`, which does not mention balance. We catch it, read `getBalance`, and rewrite it ourselves. `Insufficient funds` would be a much better message.
- **Faucet ran dry mid-hackathon.** A claim failed with `insufficient funds for gas * price + value: have 9995400999990802000 want 10000000000000000000`: the faucet's payout wallet (`0x815A…C712`) held 9.9954 GLM but each claim sends exactly 10. Every claim failed until it was topped up. A payout smaller than the balance, or an alert when the faucet is low, would avoid it.
- **The node rejects uppercase attribute names, but the SDK says they're fine.** `createEntity` with an attribute called `createdAt` fails on Tiramisu with `an attribute name holds "A" (0x41) at byte 7, which is outside the name charset ("A"-"Z", "a"-"z", "0"-"9", ".", "-" and "_", with a letter first)`: the message lists `A-Z` as allowed while rejecting `A`. The SDK's own validator (`names.ts`: `/^[A-Za-z][A-Za-z0-9._-]*$/`, "names are case-sensitive") and its docs accept camelCase, so `createdAt`, `postKey` etc. pass client-side and only fail on-chain. We renamed everything to `snake_case` (`created_at`, `post_key`, `entry_key`…). Repro: `createEntity({ attributes: { createdAt: 1 }, ... })`.
- **Gas: a small balance isn't enough, and the error doesn't say so.** A wallet with 0.001 GLM could not write (`Execution error without revert data`) while 0.01 GLM could, so the node seems to require balance for a generous gas limit up front, not just what the transaction burns (real cost was ~0.0001 GLM per transaction at 1 gwei). Our seed run used 0.03 GLM per wallet for ~120 entities each.
- **`executeBatch` made seeding practical.** 2,486 synthetic entities (21 wallets, batches of 25 per transaction, wallets in parallel) landed in a few minutes. Dependent entities (comments → posts) need the parent's key first, so we write in phases and map keys from `createdEntities`.
- **Our assumed query syntax was wrong.** We had guessed `attr = "x" && n >= 1`. The real language is typed: `attr = str('x') AND n >= i32(1)`, `postKey = key(0x…)`, single quotes with `''` as the only escape. Good news: the SDK's `eq/and/or/gte` combinators render the exact string, so we now build every query with them and show that string in the "Show query" panel. Only found by reading the SDK source; the README example (`eq('category','documentation')`) doesn't show the wire syntax.
- **Numbers are typed, and `i32` is the default.** `createdAt` in ms (`~1.79e12`) overflows `i32`, so it must be tagged `u64`; a bare `number` would be rejected. Range queries only work on `i32/u64/u256/dec`, so a string-typed amount silently can't use `>=`.
- **Open question from the first draft, answered by the SDK:** can a non-owner extend an entity? Yes, if it was *created* with `permissionlessExtension: true` (an immutable creation flag). We set it on salaries so "Still accurate" can refill the life bar from any wallet. Not mentioned in the README; found in `entity/flags.ts`.
- **`readonly` flag fits our integrity story.** Every Tankha entity is created `readonly`, so even the author can't rewrite a salary after others confirmed it. We'd love an explorer badge for it.
- **Chain-derived creation time exists but isn't filterable.** `$createdAt` (block) comes back in results but `$createdAt` can't appear in a query, so feed ordering, "last 24 h" filters and burst detection still need our self-reported `createdAt` attribute (which also lets the seed script backdate synthetic data). Making `$createdAt` queryable would remove the trust-score weakness from the 10-17 entry below.
- **A query must have at least one filter and pages max out at 200.** There is no "all entities of type X" without a `type = …` predicate, and no `COUNT`. Our stats strip pages through every entity of a type just to count it. A `count` select or an `IN (…)` operator would cut dozens of round trips.
- **Expiry in blocks, not time.** `expiresAt` comes back as a block number. We convert with `arkiv_getBlockTiming` (`currentBlock`, `currentBlockTime`, `blockDuration` = 2 s). Handy, but it costs one extra call per read to show "expires in 17 months".
- **Only one public HTTP RPC is documented.** The RPC switcher (a censorship-resistance demo moment) needs ≥ 2 endpoints; we list the one official endpoint and let users add their own.
- **`select()` typing footgun:** `select({...})` must be called with an inline literal, otherwise TypeScript widens `true` to `boolean` and every field becomes a compile error (documented in the SDK README, but easy to hit when sharing a selection constant).

## 2026-10-17 — frontend (social layer)

- **New posts start "Unusual" (resolved).** Under the original formula, a fresh-wallet post with no peer group scores 30, below Medium, so honest new posts were hidden. Resolved with a 72 h "New" grace period for unflagged posts (see `isNew` in `lib/trust.ts`). Flagged bursts get no grace.
- **Votes are sybil-cheap.** Any tab can mint a fresh wallet and vote. We kept votes out of the trust score entirely for that reason, so they only affect ranking. A real deployment would weight votes by wallet history, or cap per-wallet influence.
- **Votes are append-only entities.** Every vote change is a new entity, and the latest one per (wallet, target) wins. That's simple and needs no updates or deletes, but the vote set only grows (until expiry). A per-(wallet, target) upsert would be nicer if Arkiv supports owner updates cheaply.
- **Feed = load everything.** The feed pulls every salary, review, comment and vote, then ranks client-side so anyone can reproduce the order. Fine at hackathon scale (hundreds of entities). It needs pagination or a time window beyond a few thousand.

## 2026-10-17 — frontend

- **Self-reported timestamps.** `createdAt` is an attribute the poster writes, so it can be backdated or forward-dated. Trust scoring (wallet age, burst detection, freshness) leans on it. We'd prefer a chain-derived creation time (block of creation) exposed on read; until then it's a known weakness.
- **Wallet history only sees unexpired data.** "Wallet first seen" is computed from live entities. Once a wallet's oldest entries expire, it looks younger than it is. Expiry is a feature, so this is a trade-off, not a bug — noted for the README.
- **Peer-median poisoning.** First version of range-fit let a sybil burst drag the peer median up, which flagged *honest* entries as "Unusual 0.4×". Fixed by excluding Burst-flagged entries from peer medians (two-pass, since burst detection doesn't depend on peers). Not Arkiv-specific, but anyone building reputation on open data will hit it.
- **Bulk confirmation lookups.** Fetching confirmations for ~150 entries with an OR-list makes a very long query string. Above 20 keys we fetch all `confirmation` entities and filter client-side. Would love an `IN (…)` operator or similar.
- **Query syntax unconfirmed (resolved 10-18).** See the 10-18 entry: it is typed (`str('x')`, `i32(1)`).
- **Burner wallets vs. confirmations.** Fresh wallets are single-use (good for anonymity), which also means a poster can confirm their own entry from a second burner. "Owner can't confirm" only stops the naive case. Confirmations from wallets with no history currently count fully; weighting confirmations by the confirmer's wallet age would be the next step (not in the spec'd trust formula yet).
- **Next 16 static export + prefetch.** The export writes segment-prefetch payloads as `route/__next.route/__PAGE__.txt`, but the client requests `route/__next.route.__PAGE__.txt` → 404 on every static host (would also hit IPFS). Fixed with a `postbuild` script (`scripts/flatten-prefetch.mjs`) that writes the dotted copies.
- **Static export.** No server means no place for secrets, so the "fresh wallet" flow must fund burners from the browser. Depends on whether Tiramisu has a programmatic faucet.
